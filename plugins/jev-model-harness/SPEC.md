# 모델 라우터 플러그인 스펙 (jev-model-harness)

> 상태: 구현 v0.2 (Claude Code + Codex) · 작성일 2026-10-13 · 작성: 차명근, Claude
> 방식: SDD (스펙을 먼저 확정하고, 이 문서를 기준으로 구현한다)

## 1. 개요

Claude Code에서 대화할 때, 사용자 입력마다 Jev(TypeSafe AI의 System One 모델)로 요청의 성격을 빠르게 판단해서
**넘길 가치가 있는 작업만 더 싼 모델의 서브에이전트로 보내는** Claude Code 플러그인.

메인 대화는 항상 Opus가 맡는다. 메인 모델이 바뀌지 않으므로 메인 대화의 프롬프트 캐시가 깨지지 않는다.
Codex에서도 같은 판단 로직을 쓴다. Codex에서는 메인이 gpt-6.1-sol이고, Luna에만 위임한다. (11장)

## 2. 목표 / 비목표

**목표**
- 품질 손해 없이 API 비용(구독 사용 시에는 사용 한도 소모)을 줄인다.
- 무거운 작업과 가벼운 작업이 예측 없이 번갈아 와도 캐시 손실이 생기지 않게 한다.
- 모든 라우팅 결정을 기록해서 기준값을 데이터로 조정할 수 있게 한다.

**비목표**
- 메인 대화의 모델 자체를 자동으로 바꾸지 않는다. (캐시 손실 때문. 근거는 7장)
- Claude Code 밖의 독립 API 앱은 이 스펙의 범위가 아니다. (나중에 같은 규칙으로 별도 진행 가능)

## 3. 구조

```
사용자 입력
   │
   ▼
[UserPromptSubmit 훅] ── Jev 1회 호출 (질문 3개 병렬 처리)
   │
   ▼
판단 결과를 메인(Opus)에게 지시로 전달
   ├─ 메인이 직접 처리
   ├─ haiku-worker 서브에이전트에게 위임
   └─ sonnet-worker 서브에이전트에게 위임
```

| 구성요소 | 역할 |
|---|---|
| 메인 모델 | Opus 5.5 고정 |
| 훅 (`UserPromptSubmit`) | 입력을 받아 Jev를 호출하고, 라우팅 지시를 메인에게 전달 |
| `haiku-worker` 서브에이전트 | `model: haiku`. 파일 탐색, 검색, 대량 읽기 |
| `sonnet-worker` 서브에이전트 | `model: sonnet`. 범위가 명확한 구현·수정 |
| 로그 파일 | 매 판단 기록 (R8) |

## 4. Jev 질문 정의

한 번의 호출로 세 질문을 함께 보낸다. Jev는 질문들을 같은 입력에 대해 각각 독립적으로, 병렬로 평가한다.

**입력(`state`)**: 사용자 메시지 + 직전 대화 요약.
현재 사용 중인 모델 정보는 넣지 않는다. (판단이 현재 모델 쪽으로 쏠리는 것을 막기 위해)

### 4.1 `standalone` (Noul)
> 이 요청은 이전 대화 맥락 없이도 처리할 수 있는가?

### 4.2 `bulk` (Noul)
> 이 요청은 파일 여러 개를 읽거나 코드를 많이 작성해야 하는 작업인가?

### 4.3 `level` (Score, 3단계)
> 이 요청을 처리하려면 어느 수준의 AI 모델이 필요한가?

| 단계 | 설명 | 예시 |
|---|---|---|
| 0 | 단순 조회: 사실 확인, 짧은 질의응답, 파일 위치 찾기, 한 줄 설명 | "이 함수 어디 있어?", "git status 결과 설명해줘" |
| 1 | 일반 구현: 범위가 명확한 코드 작성·수정, 버그 수정, 테스트 추가 | "결과 화면에 날짜 표시 추가해줘", "이 에러 고쳐줘" |
| 2 | 설계·기획: 구조 결정, 여러 파일에 걸친 설계, 트레이드오프 판단, 요구사항 정의 | "플러그인 구조 설계하자", "이 기능을 어떻게 나눌지 기획해줘" |

사용하는 값은 다음과 같다.
- 판단에는 `probabilities`와 `confidence`를 쓰고, `score`는 반올림한 단계와 기록에만 쓴다.
- `confidence`는 확률이 한 단계에 얼마나 몰렸는지를 나타낼 뿐, 정답일 가능성이 아니다.

## 5. 판단 흐름

```
Jev 1회 호출 → { standalone, bulk, level }
   │
   ├─ ① standalone < 0.8        → 메인(Opus). 끝
   ├─ ② bulk < 0.8              → 메인(Opus). 끝
   ├─ ③ level.confidence < 0.5  → 메인(Opus). 끝
   └─ ④ round(level.score)
          0 → haiku-worker
          1 → sonnet-worker
          2 → 메인(Opus)
```

## 6. 규칙

| # | 규칙 | 내용 |
|---|---|---|
| R1 | 판단 시점 | 사용자 입력마다 1회 판단한다. Jev는 한 번 호출로 세 질문을 처리한다. 작업 도중에는 바꾸지 않는다 |
| R2 | 맥락 필요 | `standalone < 0.8`이면 메인이 처리한다. 확실히 독립적인 요청일 때만 위임한다 |
| R3 | 분량 부족 | `bulk < 0.8`이면 메인이 처리한다. 위임하는 비용이 아끼는 비용보다 크기 때문이다 |
| R4 | 애매함 | `level.confidence < 0.5`이면 메인이 처리한다 |
| R5 | 위임 | `round(level.score)`가 0이면 haiku-worker, 1이면 sonnet-worker, 2면 메인이 처리한다 |
| R6 | 서브에이전트 재사용 | 같은 종류의 서브에이전트를 마지막으로 쓴 **요청의 시작 시각**에서 캐시 수명(5분 또는 1시간)이 지나지 않았으면 새로 만들지 않고 이어서 쓴다. 가능하면 `cache_read_input_tokens`로 캐시가 실제로 남아 있는지 확인한다 |
| R7 | 수동 우선 | `!opus` / `!sonnet` / `!haiku`로 강제 지정하고, `!auto`로 자동 모드로 돌아온다. 수동 지정이 항상 이긴다 |
| R8 | 기록 | 세 질문의 답(전체 값), 결정, 적용된 규칙 번호, 비용을 매 판단마다 기록한다 |
| R9 | 장애 대비 | Jev 호출이 실패하거나 시간 제한을 넘기면 메인이 처리한다. 라우터가 실패해도 대화는 막히지 않아야 한다 |

0.5 같은 기준값은 출발점이다. R8 로그가 쌓이면 데이터로 조정한다.

## 7. 비용 근거

### 7.1 가격 (100만 토큰당, Anthropic 1st-party API, 2026-10 기준)

| 모델 | 입력 | 출력 | 캐시 쓰기 (5분, 1.25배) | 캐시 쓰기 (1시간, 2배) | 캐시 읽기 |
|---|---|---|---|---|---|
| Haiku 5.5 | $0.10 | $0.50 | $0.125 | $0.20 | $0.01 |
| Sonnet 5.5 | $2.00 | $10.00 | $2.50 | $4.00 | $0.20 |
| Opus 5.5 | $4.00 | $20.00 | $5.00 | $8.00 | $0.20 |
| Jev | $0.042 | 무료 | – | – | – |

### 7.2 이 구조를 고른 이유
- **캐시는 모델별로 따로 저장된다.** 메인 모델을 바꾸면 지금까지의 대화 전체를 새 모델 캐시에 다시 써야 한다.
  40턴 시뮬레이션에서 뒤섞인 요청마다 모델을 바꾸고 캐시가 만료되면 비용이 $5.51였다. Opus만 쓸 때는 $2.39로, 2.3배 차이가 난다.
- **캐시 읽기 비용은 Opus와 Sonnet이 같다** ($0.20). 그래서 메인을 Opus로 고정해도 입력 쪽 부담이 작다.
- **절약은 두 곳에서 나온다.**
  - 구현 작업을 Sonnet에 넘기면 출력 비용이 절반이 된다.
  - 대량 읽기를 Haiku에 넘기면 입력 비용이 40분의 1이 된다.
  - 위임한 작업의 중간 과정이 메인 대화에 쌓이지 않아서 메인 대화가 가볍게 유지된다.
- **캐시 수명은 요청이 시작된 시각부터 센다.** 생성 시간도 포함된다. 캐시를 읽으면 타이머가 다시 시작된다.
  그래서 도구를 연달아 호출하는 긴 작업에서도 캐시가 유지된다. 캐시가 만료되는 주된 원인은 사용자가 오래 쉬는 경우다.

### 7.3 주의
Claude Code를 구독(Pro/Max)으로 쓸 때는 절약 효과가 달러가 아니라 사용 한도로 나타난다.

## 8. 구현 전 확인 결과 (2026-10-13)

### 8.1 확인 완료
- [x] **위임 지시 주입**: `UserPromptSubmit` 훅의 `hookSpecificOutput.additionalContext`로 메인 모델에게 지시를 넣을 수 있다.
  단, 이 지시는 **권고일 뿐 강제가 아니다.** 프롬프트 자체를 바꿀 수는 없다. (code.claude.com/docs/en/hooks)
- [x] **메인 모델 자동 전환 불가**: 훅이나 플러그인으로는 메인 모델을 바꿀 수 없다. `/model`, 설정, CLI 옵션으로만 가능하다. 2장 비목표와 일치한다.
- [x] **Jev 호출**: REST API(`POST https://api.typesafe.ai/v1/systemone`, `Authorization: Bearer`)와 JS SDK(`@typesafe-ai/sdk`, Node 20 이상)가 모두 있다.
  이 PC는 Node v24.19.0이라 사용 가능하다. 모델명은 `jev-latest`.
- [x] **서브에이전트**:
  - frontmatter의 `model: haiku` / `sonnet`으로 지정한다. 플러그인의 `agents/` 폴더에 넣어 배포할 수 있다.
  - `SendMessage`로 이어서 쓰면 대화 기록이 유지되고, 처음 실행 때 데운 캐시를 다시 읽을 수 있다. R6 구현이 가능하다.
- [x] **캐시 사용량 읽기**: 이 PC의 실제 대화 기록(JSONL)에서 `model`, `cache_read_input_tokens`, `cache_creation_input_tokens`, `ephemeral_1h_input_tokens`가 확인됐다.
  다만 **공식 문서에 없는 형식**이라 바뀔 수 있다. 읽기 실패 시 시간 기준으로 대체한다.
- [x] **API 키 관리**: `plugin.json`의 `userConfig`에 `sensitive: true`로 선언하면 OS 보안 저장소에 보관된다.
  훅에서는 `CLAUDE_PLUGIN_OPTION_<KEY>` 환경변수로 읽는다.

### 8.2 설계에 반영할 사항
- **훅 시간 제한**: UserPromptSubmit의 기본 시간 제한은 30초다. 명시적으로 짧게(예: 3초) 둔다.
  시간 제한을 넘기면 출력이 버려지고 입력은 막히지 않는다. 이 경우 "지시 없음"이 되어 메인이 처리하므로 R9가 자연히 충족된다.
- **환경변수 충돌**: 사용자 환경에 `CLAUDE_CODE_SUBAGENT_MODEL`(특히 `_FORCE=1`)이 설정돼 있으면, frontmatter의 모델 지정이 조용히 무시된다. 훅에서 이를 감지해 경고한다.
- **Noul에는 confidence가 없다**: 값은 "yes일 확률"(0~1)이다. 문서의 라우팅 예시는 0.8 이상이면 yes, 0.2 이하면 no, 그 사이는 보류로 나눈다. → 9장 미결 사항
- **Jev 특성**:
  - 주 학습 언어가 영어라서 질문(`instructions`)과 기준표는 영어로 쓰고, 예시와 `state`만 한국어로 둔다.
  - 부정문과 이중부정에 약하므로 질문은 긍정문으로 쓴다.
  - `state`에 관계없는 내용이 들어가면 정확도가 떨어지므로 최소한만 넣는다.
- **plugin 서브에이전트 제약**: 플러그인에 포함된 서브에이전트는 `hooks`, `mcpServers`, `permissionMode` 설정이 무시된다. 도구는 `tools` 목록으로 제한한다.

### 8.3 구현 후 검증 (2026-10-13)
- [x] **프롬프트 필드 이름은 `prompt`**: 실제 Claude Code(2.1.296)에서 훅 로그에 프롬프트가 정상 기록됐다.
- [x] **Jev 응답 시간**: 측정 3회(46건) 중앙값 약 200ms, 최대 472ms. 실제 훅 전체 처리 시간은 약 250ms다.
- [x] **한국어 판단 품질 (1차)**: 질문 문구를 고칠 때 보지 않은 검증용 14건 중 11건이 기대와 일치했다. 잘못된 위임은 0건이고, 놓친 3건은 모두 메인이 처리하는 안전한 쪽이었다. (`bench/`)
- [x] **위임 지시 준수 (1차)**: `claude -p` 자동 테스트 4건이 모두 기대대로 처리됐다.
  - 조회 요청은 haiku-worker로, 구현 요청은 sonnet-worker로 갔다.
  - 맥락 의존 요청(R2)과 개념 질문(R3)은 메인이 처리했다.
  - 위임 지시가 나간 2건 모두 Opus가 따랐다.
- [x] **캐시 수명 감지**: 이어지는 대화에서 대화 기록을 읽어 1시간 캐시를 감지했다. 새 세션의 첫 요청은 기록이 없어서 기본값 5분을 쓴다.
- [ ] **실제 세션 20개 이상의 로그로 재검증** (10장 완료 기준). 표본이 아직 작다.

## 11. Codex 지원 (v0.2)

판단 로직(Jev 질문, 규칙 R1~R5)은 그대로 두고, 판단 결과를 **단계(tier)**로 낸다.
- `light`: 단계 0
- `mid`: 단계 1
- `main`: 단계 2, 또는 R2~R4로 메인이 처리하는 경우

단계를 실제 워커로 바꾸는 일은 플랫폼별 설정(`scripts/lib/platforms.mjs`)이 맡는다.

### 11.1 단계별 모델

| 단계 | Claude Code | Codex |
|---|---|---|
| main (메인) | Opus | gpt-6.1-sol |
| mid | sonnet-worker (Sonnet) | **메인이 처리** |
| light | haiku-worker (Haiku) | luna_worker (gpt-6-luna) |

Codex에 mid 워커가 없는 이유는 다음과 같다.
- 메인 gpt-6.1-sol과 gpt-6-sol은 가격이 같다 (Codex 크레딧, 100만 토큰당 입력 50 / 출력 250). 위임해도 아끼는 것이 없다.
- Luna는 입력 2.5 / 출력 12.5로, Sol의 20분의 1이다.
- 사용자가 처음 말한 이름 luna/terra/sol은 이전 세대(GPT-5.6) 이름이다. 이 세대는 모델 ID가 문서에 없고, 신세대로 넘어가는 동안만 유지된다. 그래서 현재 세대(GPT-6)를 쓴다.

### 11.2 Codex에서 달라지는 점

| 항목 | Claude Code | Codex |
|---|---|---|
| 플랫폼 감지 | 기본값 | 훅 입력에 `turn_id`가 있으면 Codex. `MODEL_ROUTER_PLATFORM`으로 강제할 수 있다 |
| 매니페스트 | `.claude-plugin/plugin.json` | 루트 `plugin.json`의 `extensions["com.openai"].hooks`, 호환용 `.codex-plugin/plugin.json`의 `hooks` |
| 훅 파일 | `hooks/hooks.json` | 같은 파일 |
| 서브에이전트 배포 | 플러그인 `agents/`에 포함 | **플러그인에 포함할 수 없다.** `npm run setup:codex`로 `~/.codex/agents/`에 복사한다 |
| 위임 지시 | Agent 도구와 `subagent_type`을 지정 | 자연어 ("Have the `luna_worker` subagent handle this request") |
| R6 서브에이전트 재사용 | `SendMessage`로 이어서 쓰기 | 문서화된 방법이 없어 사용하지 않는다 |
| 메인 모델 확인 | 대화 기록에서 읽는다 (두 번째 입력부터) | 훅 입력의 `model`로 읽는다 (첫 입력부터) |
| 훅 신뢰 | 필요 없음 | 사용자가 `/hooks`에서 한 번 신뢰 승인해야 한다 |
| 직전 답변 / 캐시 수명 | 대화 기록에서 읽는다 | 기록 형식이 공개되지 않아 읽지 않는다. 직전 답변 없이 판단한다 |
